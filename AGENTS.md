# AGENTS.md

## КРИТИЧЕСКОЕ ПРАВИЛО №1 — коммит и push любого прод-изменения

**Любое изменение, попадающее в Telegram-продакшн, обязано сразу коммититься и пушиться в GitHub-репозиторий `tondyor/sawapapp`.**

- Продакшн = всё, что деплоится на платформу Telegram: `npx tgcloud push` (модули `tgcloud/` + сборка Mini App), `npx tgcloud migrate` (изменения схемы БД), правки фронтенда, уходящие в прод.
- Порядок работы без исключений: изменение → деплой/миграция в прод → `git add` → `git commit` → `git push` в `origin/main`. Промежуток между деплоем в прод и push'ем в GitHub минимален.
- Нельзя оставлять прод-изменения только в рабочей папке или только в облаке: состояние без коммита в GitHub считается потерянным (история проекта — единственный источник истины о том, что и когда менялось).
- Исключений нет. Если push невозможен (нет сети, ошибка git) — изменение не считается завершённым: сообщить пользователю в чат и довести push до успеха.

## АРХИТЕКТУРА ПРОДА (читать до любых правок)

### Что это
SAWAP — Telegram-прод: Mini App (чат с AI-агентами ролей) + бэкенд на **Telegram Serverless** (изолят V8 рядом с Bot API, своя SQLite-БД, исходящий HTTP только через SDK). Чат-бот в Telegram — только меню выбора агента (`/start`, `/agents`, `callback_query`); весь агентный рантайм — в Mini App: ход → планирование → исполнители → синтез; трасса — в `turn_events`, клиент опрашивает `getTurnEvents` и шлёт `runTurnStep`/`finishTurnSynthesis` цепочкой коротких вызовов.

### Окно ответа (главное ограничение)
- **Документировано:** у Telegram НЕТ лимита времени выполнения обработчика; ответ обязан уйти клиенту черновиком `sendMessageDraft`/`sendRichMessageDraft` (эфемерный предпросмотр ~30 с, пустой текст = «Thinking…»); финал — обязательным `sendMessage`/`sendRichMessage`; эфемерки — 15 с; вызовы `answerPreCheckoutQuery` — 10 с.
- **Измерено (не документировано, 20+ прогонов):** любой вызов дольше ~28–34 с возвращается с HTTP 500 и изолятор прекращает работу, всё несохранённое состояние теряется; таймеры внутри изолятора мёртвые (`setTimeout` нет, `AbortSignal.timeout` тоже не помогает).
- **Вывод:** любой один вызов LLM не должен превышать ~25 с ИЛИ должен оставлять чекпоинт в БД каждые ~6 с; долгая генерация ведётся кусками с продолжением «ровно с места обрыва».

### Обязательный UX AI-ботов в чате
Бот обязан сразу слать черновик (`Thinking…`), дальше `sendDraft` по мере генерации, финал — `sendMessage`/`sendRichMessage` (богатое сообщение — 32 768 знаков, таблицы/формулы/thinking-блок). `can_stop:true` → апдейт `stopped_message_generation` → остановка модели/очереди.

### Модели (текущие настройки БД; код — фолбэк)
Прод отвечает только **Ultra-550b** (TTFB ~0.6 с, всегда отдаёт байты) и **Bolt-e4b** (статусы трассы, ~0.4–11 с). **Muse-30b, Mistral-4-1T, DeepSeek-4.1, step-5 — с сервера байтов не отдают** (локально отвечают; на проде не проходят даже до первого токена). Роли: DEFAULT/ANSWER/PLANNER/COMPRESS/MATH/DEEP_REASON = Ultra-550b; статусы = Bolt-e4b; зрение = Super-VL-120b; парсинг = Parse 2.0 (не тестировался на проде). Настройки БД переопределяют константы в коде (`getSettingOr`): сменить модель можно `endpoints/adminSetSetting` без деплоя.

### Как всё хранится и чинится
- `turns` (ход: план, находки, `stepText`/`answerText` — чекпоинты), `turn_events` (трасса), `messages`, `conversations` (поле `checkpoint` — компактизация истории > 250k токенов через Ultra в `<conversation-checkpoint>`), `settings` (ключ+значение; `NVIDIA_API_KEY`, `SERPER_API_KEY`, роли моделей).
- Деплой: `npx tgcloud push` (код), `npx tgcloud migrate --yes` (схема БД; push никогда не меняет БД сам). Тестовые LLM-прогоны на проде — только с явного разрешения; перед деплоем обязательно `esbuild`-парсинг изменённых файлов и живой прогон хода.
- Полный конспект (не в git, локальный): `docs/telegram/*.md` — читать при любой работе с Telegram.
- **Нельзя:** объяснение сбоев «не работает модель / Telegram не даёт» без привязки к источнику; «починили» без прогона хода до `done`; непроверенные деплои; писать замер как «документировано».
